# Deployment and operations

## Installation isolation

Use a new PostgreSQL database, database role, auth secret, application origin and email sender for every installation/environment. Never reuse another deployment's environment file or connect tests to it. Public releases begin at migration 0001 and do not require an existing application or cloud project.

Node.js 22+ and PostgreSQL 16+ are supported. The local Compose database listens only on `127.0.0.1:54329` and uses the random password generated by `npm run setup`. Volumes persist across restarts. `docker compose --env-file .env.local down` keeps the volume; adding `-v` deletes its data. For native PostgreSQL create an empty database and update both URLs.

## Configuration

| Variable | Use |
| --- | --- |
| `DATABASE_URL` | Application database URL; pooled connection allowed |
| `DATABASE_URL_UNPOOLED` | Direct URL to the same database for migration transactions |
| `BETTER_AUTH_SECRET` | Unique high-entropy secret; setup generates it |
| `BETTER_AUTH_URL` | Exact external origin: `https://booking.example.com`, no path; localhost only in development |
| `MAX_OWNERS` | Non-negative integer; zero = unlimited owner/dog pairs, positive = account cap including paused owners |
| `GMAIL_USER`, `GMAIL_APP_PASSWORD` | Your Gmail sender and app password; blank disables sending |
| `CRON_SECRET` | Unique random bearer secret for HTTP cron endpoints |
| `ALLOW_TEST_DATABASE`, `TEST_DATABASE_HOST` | Destructive test/sample safeguards; keep false in real environments |
| `POSTGRES_PASSWORD` | Local Compose database password; must match local database URLs |

Do not prefix secrets with `NEXT_PUBLIC_`. Hosted PostgreSQL connections must verify TLS (`sslmode=verify-full` with the correct CA where required). SMTP TLS verification stays enabled. Use an unprivileged runtime database role; migrations need schema/DDL permissions. Set credentials in your host's secret manager, not in source control, images, command history, screenshots or logs.

## Ordinary Node server

1. Clone the public repository, `npm ci`, and generate/edit `.env.local`. Restrict file permissions to the operator. Provision an empty database.
2. Run `npm run db:migrate`. Migrations run transactionally under an advisory lock and record SHA-256 checksums; reruns are safe, but applied SQL files must not be edited.
3. Run `npm run account:admin -- "Your name" you@example.com`. Open `.local/admin-invitation.txt` privately and consume the link. For recovery use the same command with `recover` as its final argument.
4. Run `npm run build`, then `npm start` under a process manager. Put a TLS reverse proxy in front. Limit request sizes (for example 32 KB), rate-limit abusive traffic, and overwrite—not pass through—client-supplied `X-Real-IP`. Better Auth and invitations use that trusted header for rate limits.
5. Schedule `npm run worker` from the checkout directory **every minute**, using the same private environment. For example with systemd, configure `WorkingDirectory=/srv/dogbooker`, `ExecStart=/usr/bin/npm run worker`, and a timer with `OnCalendar=*-*-* *:*:00`. Use an absolute npm path valid on your host. Persist scheduler logs without payloads and alert on failures.
6. Exercise invitations, owner request, administrator approval, cancellation, time-change proposal and mail delivery using accounts you control. Test backups and restoration before inviting real owners.

The worker handles ordinary queued mail and missing-time reminders. It is safe for competing invocations because database leases/unique keys fence jobs. It processes at most two messages per invocation; the page/API also drains jobs after requests. Monitor backlog and `needs_review`. A scheduler outage past the reminder date requires manual follow-up; stale reminders are intentionally skipped.

## Email

Optional email uses your Gmail account with an app password. Follow [Google's app-password instructions](https://support.google.com/accounts/answer/185833); availability depends on your account/security policy. Set the two Gmail variables and restart the application/worker. Sender is `DogBooker <GMAIL_USER>` over verified TLS to Gmail port 465. Do not place a normal account password here. Invitations are shared manually; booking lifecycle/time messages use the outbox.

First test with your own addresses. SMTP acceptance means provider acceptance, not inbox delivery. Verify actual receipt. No live email credentials are required by tests; transports are stubbed and synthetic fixtures refuse real sending credentials. If mail was disabled while testing with fixtures, discard that disposable database before enabling a real sender.

A `needs_review` job may have been delivered already. Inspect your provider records before any recovery. Never reset all jobs to pending. Switching sender/origin after the first attempt may leave frozen messages requiring review. Queries for monitoring should expose aggregate counts/status, not recipient or message content.

## Vercel (new independent project only)

Create a new Vercel project importing your own clone/fork and a new PostgreSQL database. Set runtime environment variables in that project, including both database URLs where needed. Run migrations explicitly against the new database before deployment. Do not run migrations during a build; preview builds must never receive production database credentials.

The existing `workflow/next` integration supports durable reminder runs. If using that scheduler, configure authenticated GET cron calls to `/api/reminders` daily before 09:00 Stockholm (for example 04:00 UTC year-round); this schedules separate durable wakeups at 09:00. Configure `/api/notifications` at least every minute for delivery retries where your plan supports that frequency. Vercel supplies `Authorization: Bearer CRON_SECRET` for its cron calls. Check your plan's [cron frequency/precision limits](https://vercel.com/docs/cron-jobs/usage-and-pricing); a daily mail retry job is insufficient for timely general notifications. Use an external authenticated scheduler or the ordinary Node worker if needed.

For the portable scheduler use the CLI worker on an always-on worker host. Do not depend on local Workflow disk state on ephemeral hosts. No Vercel project ID, team, region, database endpoint or deployment linkage is shipped in this repository.

## Updates, backup and rollback

Back up PostgreSQL before migration; encrypt backups and routinely restore into an isolated environment. Pin deployment to a reviewed commit and run CI on updates. Keep compatible application artifacts for rollback; do not reverse exclusion constraints after overlapping dog stays exist. Favor a forward fix for schema changes. Database restore is a planned outage/reconciliation operation, never an automatic rollback step.

Review auth/session, booking history and notification retention for your jurisdiction. Limit administrator access; rotating an auth secret may end sessions. Deactivation preserves booking history. This release has no self-service erasure/export workflow; operators must handle those requests securely at the database/application administration layer. See the security policy for vulnerability reporting.
